## ADR-001 MySQL 8 作为唯一数据库

**状态**：已接受（1.0）

**背景**：小程序 1.0 的数据量级为「万级用户、十万级帖子、百万级埋点」，读多写少，团队熟悉 MySQL；上游会议材料也指定 MySQL；不需要全文检索、时序、地理等特殊能力。

**决策**：使用 MySQL 8.0 单实例、单库 `jianheng`；字符集 `utf8mb4`；不使用 Redis（1.0 QPS 低）、不引入 Elasticsearch。

**备选与放弃原因**

| 备选 | 放弃原因 |
|---|---|
| PostgreSQL | JSON 与索引能力更强，但团队栈与部署脚本已按 MySQL 准备，收益不足以抵消迁移成本 |
| SQLite | 并发写入弱，多 uvicorn worker 下会锁表 |
| MongoDB | 关系（关注/点赞/收藏）需要多次 join，文档模型反而更绕 |

**后果**
- ✅ 部署简单、备份成熟、DBA 友好。
- ⚠️ 全文搜索只能 `LIKE`，数据量上来后需加 `ngram` 全文索引或外部搜索（记入 1.1 待办）。
- ⚠️ 单实例无高可用，1.0 接受（故障恢复靠备份 + 重启）。

## ADR-002 不建物理外键，只在应用层保证一致性

**状态**：已接受

**背景**：内容型业务存在大量级联（删帖要删图、删评论要删回复、删用户要处理内容）。物理外键会在批量操作时带来锁竞争与迁移困难；且 0.1 已有"应用层事务"的实现习惯。

**决策**：所有关联只建索引，不建 `FOREIGN KEY`；级联删除由 Service 层在同一事务内完成；每日对账脚本检查孤儿数据（如 `post_images.post_id` 不存在）。

**备选与放弃原因**
- 建物理外键：可强约束，但 `posts` 与 `post_images` 的高频写入会放大锁范围，且 Alembic 改表更麻烦。

**后果**
- ✅ 写入快、迁移灵活、可分库。
- ⚠️ 依赖代码正确性 → 必须有：①Service 层统一封装级联删除；②每周孤儿数据巡检；③集成测试覆盖删除路径。

## ADR-003 内容用「软删 + status 双字段」

**状态**：已接受

**背景**：帖子既可能被作者删除（`deleted`），也可能被管理端下架（`hidden`），未来还可能有审核中（`reviewing`）。若只用一个 `deleted` 布尔，无法区分"作者删的"和"平台下架的"，也无法支持申诉与审计。

**决策**
- `deleted TINYINT(1)`：作者删除标记（软删，保留数据）。
- `status VARCHAR(20)`：`published` / `hidden`（平台下架）/ `reviewing`（审核中，1.0 不产生）/ `deleted`（与 `deleted=1` 同步）。
- 对外查询统一条件：`status='published' AND deleted=0`。
- 作者本人可查到自己的 `hidden/deleted` 内容（详情页返回 200 + 状态，列表过滤）。

**备选与放弃原因**
- 单 `deleted`：无法区分下架与自删，管理端无法审计。
- 单 `status`：删除需要改动业务语义（`deleted` 是状态之一），但统计「作者删除量」时不便；两者并存成本很低。

**后果**
- ✅ 支持审计、申诉、恢复；统计口径清晰。
- ⚠️ 每个查询都必须带两个条件 → 用 Repository 统一封装 `visible_filter()`，禁止散落。

## ADR-004 点赞/收藏用多态单表

**状态**：已接受

**背景**：点赞可作用于帖子与评论；收藏可作用于帖子、课程、产品、话题。若每种组合一张表，会有 2 + 4 = 6 张结构几乎相同的表。

**决策**：`likes(user_id, target_type, target_id)`、`collections(user_id, target_type, target_id)`；唯一键 `(user_id, target_type, target_id)`；`target_type` 用字符串（`post/comment/course/product/topic`）。

**备选与放弃原因**
- 每类一张表：查询简单，但新增类型要建表 + 改代码 + 写迁移，扩展性差。
- 单表 + 外键：多态无法建外键，已由 ADR-002 统一放弃。

**后果**
- ✅ 新增收藏类型零 DDL；"是否已赞"查询一条 SQL。
- ⚠️ 无法用外键保证 `target_id` 有效 → 由删除逻辑负责清理（删帖时删 `likes/collections`），并有孤儿巡检。
- ⚠️ `target_type` 需在应用层用枚举校验，拒绝任意字符串。

## ADR-005 冗余计数列 + 事务内增减

**状态**：已接受

**背景**：信息流每条帖子要显示点赞/评论/收藏数，话题要显示参与人数与内容数，课程/产品要显示收藏数。若实时 `COUNT(*)`，一次列表 10 条就要 30 次聚合。

**决策**：在 `posts/topics/courses/products/comments` 上冗余计数列；写操作在同一事务内 `UPDATE ... SET x = x + 1`；每日 02:00 对账脚本用 `COUNT(*)` 修正漂移。

**备选与放弃原因**
- 实时聚合：简单但列表性能差（N+1）。
- 计数表单独存：多一次 join，收益不明显。

**后果**
- ✅ 列表查询零聚合，P95 稳定。
- ⚠️ 并发下需用 `x = x + 1`（不是读改写）；取消操作要防"减到负数"（`WHERE x > 0`）。
- ⚠️ 必须有对账，且对账要幂等。

## ADR-006 游标分页用于信息流/评论，offset 分页用于管理列表

**状态**：已接受

**背景**：信息流与评论是"无限下拉"，offset 分页在数据插入时会导致重复/漏条（经典 `page=2` 漂移问题）。而收藏、课程、搜索是"可跳页"的固定结果集，offset 更直观。

**决策**
- 信息流、评论、话题下帖子：游标分页，`cursor` = 上一页最后一条的 `id`，SQL 用 `WHERE id < :cursor ORDER BY id DESC LIMIT :size`（按时间倒序等价于 id 倒序）。
- 话题列表、课程、收藏、搜索、用户动态：`page/size` offset 分页。
- 两种分页都返回 `hasMore`。

**备选与放弃原因**
- 全部 offset：信息流会抖动。
- 全部游标：前端"跳到第 N 页"无法实现，且总数统计要额外查询。

**后果**
- ✅ 信息流无重复/漏条，性能稳定（索引 + LIMIT）。
- ⚠️ `cursor` 是不可解析字符串，前端不得依赖其格式。
- ⚠️ 按"热度"排序的话题流无法用 id 游标 → 用 `(like_count, id)` 复合游标（1.0 数据量小，先按 id；记入 1.1 优化）。

## ADR-007 时间统一 DATETIME(3)

**状态**：已接受

**背景**：`TIMESTAMP` 会随 MySQL 会话时区自动转换，容器化部署 + 多时区客户端容易"差 8 小时"；前端只需要 `YYYY-MM-DD HH:mm:ss`。

**决策**：所有时间列用 `DATETIME(3)`；连接参数 `charset=utf8mb4`；`serverTimezone` 固定 `Asia/Shanghai`；应用层统一 `datetime.now()`（服务器 TZ=Asia/Shanghai）；API 输出格式化字符串。

**备选与放弃原因**
- `TIMESTAMP`：自动时区转换看似方便，实为故障源（容器时区不一致时数据被改写）。
- `BIGINT` 时间戳：需要前后端都转换，可读性差。

**后果**
- ✅ 数据形态稳定，DBA 直接可读。
- ⚠️ 必须在 Dockerfile 与 compose 里固定 `TZ=Asia/Shanghai`，否则仍会错。

## ADR-008 主键 BIGINT 自增，对外字符串

**状态**：已接受

**背景**：小程序端 JS 的 Number 最大安全整数是 2^53-1；若用雪花 ID（19 位）会精度丢失，必须转字符串。

**决策**：主键 `BIGINT UNSIGNED AUTO_INCREMENT`；API 输出一律字符串（Pydantic `field_serializer=str`）；前端只做等值比较与拼接，不做算术。

**备选与放弃原因**
- 雪花 ID：可分布式、不可枚举；但 1.0 单库单写，无此需求，且带来精度与调试成本。
- UUID 主键：索引膨胀、可读性差。

**后果**
- ✅ 有序、紧凑、索引友好。
- ⚠️ ID 可枚举，存在遍历风险 → 内容详情按 `status` 过滤，用户接口按隐私裁剪，不暴露自增总量。

## ADR-009 产品卖点/参数、身体档案选项用 JSON 列

**状态**：已接受

**背景**：`products.features`（3 条）、`products.specs`（9 行）、`body_profiles.goals/focus_parts`（多选）都是"跟着主记录一起读写、不单独查询"的小结构。

**决策**：用 MySQL 8 的 `JSON` 列存储；写入前用 Pydantic 校验结构；读取时反序列化为对象。

**备选与放弃原因**
- EAV 子表（`product_specs`）：可查询"所有 12V 的产品"，但 1.0 无此需求，且 join 成本与代码复杂度显著上升。
- 纯文本：无法校验，前端要解析。

**后果**
- ✅ 读写一次完成，结构演进灵活。
- ⚠️ 无法用 SQL 直接筛选 JSON 内部字段（需要 `JSON_EXTRACT`，性能一般）→ 1.0 不做筛选；1.1 若需要"按参数筛选"，改为子表。

## ADR-010 camelCase 在 Pydantic 层转换

**状态**：已接受

**背景**：前端 0.1 已按 `likeCount/createdAt` 实现，不能改；Python 与 SQL 生态惯用 snake_case。

**决策**
- 数据库：snake_case。
- SQLAlchemy 模型：snake_case（与列名一致）。
- Pydantic Schema：`model_config = ConfigDict(alias_generator=to_camel, populate_by_name=True, from_attributes=True)`，`response_model` 用 `by_alias=True` 输出。
- 前端不做任何字段转换。

**备选与放弃原因**
- 前端转换：每加字段都要改两处，易漏。
- 数据库用 camelCase：MySQL 在部分系统大小写敏感，且与 Python 工具链别扭。

**后果**
- ✅ 一处转换，两端都自然。
- ⚠️ 所有响应必须声明 `response_model`，否则 alias 不生效 → 代码评审检查项。

## ADR-011 1.0 采用「先发后审」

**状态**：已接受（可通过配置回退为「先审后发」）

**背景**：0.1 用 `reviewing` + 2 分钟定时发布，纯前端模拟。1.0 若坚持先审后发，需要管理端（尚未开发），否则内容永远不可见。而社区冷启动阶段内容量小，先发后审 + 敏感词 + 举报/下架更现实。

**决策**
- 发布即 `status='published'`，立即可见。
- 敏感词前置拦截（前端 + 服务端双校验）。
- 保留 `hidden/reviewing` 状态与 `/admin/posts/{id}/review` 接口，1.1 管理端上线后按需切换。
- 配置项 `POST_MODERATION=post`（先发后审）/ `pre`（先审后发），默认 `post`。

**备选与放弃原因**
- 先审后发：合规更稳，但 1.0 无审核后台，等于发布功能不可用。
- 不做任何审核：风险高，且无法应对违规内容。

**后果**
- ✅ 1.0 可用；合规风险由敏感词 + 人工下架（1.1）+ 用户举报兜底。
- ⚠️ 提审时需向平台说明内容治理机制；若审核方要求先审后发，改配置 + 上管理端即可，无需改表。

## ADR-012 管理员独立表 admin_users

**状态**：已接受

**背景**：管理端是 Web（后续），登录方式是账号密码 + 图形验证码；小程序用户是 openid + JWT。两类身份的生命周期、权限、审计完全不同。

**决策**：`admin_users` 独立表（`username/password_hash/role`），签发 `role=admin` 的 JWT；小程序 JWT 的 `role` 恒为 `user`；两套 token 不互通（不同 `aud`）。

**备选与放弃原因**
- 复用 `users.role`：一个表混两种身份，openid 与 password 都为空值，索引与约束别扭，且管理端登录要绕过 openid 逻辑。

**后果**
- ✅ 权限边界清晰，审计独立。
- ⚠️ 两套鉴权代码 → 抽 `core/security.py` 的两个 `create_token(aud=...)` 与两个依赖 `get_current_user` / `get_current_admin`。

## ADR-013 埋点单表 track_events + 90 天清理

**状态**：已接受

**背景**：1.0 需要 12 个业务事件 + 错误事件，日增预计几千到几万条；查询场景是"按事件 + 时间范围聚合"，不做实时大屏。

**决策**：单表 `track_events`，`props` 存 JSON；按 `created_at` 建索引；定时任务每日删除 90 天前数据；写入异步（`BackgroundTasks`），失败不影响主流程。

**备选与放弃原因**
- 分表/分区：1.0 数据量不需要，运维复杂度高。
- 直接接第三方分析平台：需要外网与合规评估，且前端已有 `wx.reportAnalytics` 兜底。

**后果**
- ✅ 简单、可 SQL 直接分析。
- ⚠️ 单表增长需监控；达到千万级再考虑按月分区。
- ⚠️ `props` 必须脱敏（不含 token/openid）。

## 附：被否决的候选方案清单（避免重复讨论）

| 候选 | 结论 | 原因 |
|---|---|---|
| 引入 Redis 缓存信息流 | 1.0 不做 | QPS 低，缓存一致性成本高于收益；记入 1.1 |
| 用 Elasticsearch 做搜索 | 1.0 不做 | 数据量小，`LIKE` 足够 |
| 分库分表 | 不做 | 数据量远未到 |
| 布尔 `is_liked` 存在 posts 表 | 否决 | 与用户维度相关，无法存 |
| 把 `body_profiles` 并入 `users` | 否决 | 字段多且更新频率不同，拆表减少行宽 |
| 用 `ENUM` 类型存状态 | 否决 | 改值需 DDL，字符串更灵活 |
