## 1. 一条链路：requestId

```
Nginx（$request_id）
   │  转发头 X-Request-Id
   ▼
FastAPI 中间件（优先沿用，缺失则生成 16 位 hex）
   │  写入 ContextVar
   ├─► 响应头 X-Request-Id
   ├─► 响应体 requestId
   └─► 每条日志的 request_id 字段
   ▼
前端（services/request.js）保存最近一次 requestId
   │  失败时随 api_error 上报 / 用户截图可见
   ▼
运维：grep "request_id":"<rid>" /data/jianheng/logs/app.log
```

**规则**
1. 每个请求**必须**有 `requestId`，缺失视为缺陷。
2. 前端只透传，不生成（避免与后端不一致）。
3. 日志里 `request_id` 是**字符串**，不加引号嵌套转义错误。

## 2. 日志格式（JSON 行）

每行一个 JSON，便于 `grep` 与 `jq`：

```json
{"ts":"2026-11-04 16:12:03.421","level":"INFO","logger":"app.api.posts","request_id":"8f3c1a2b9d4e","user_id":"100001","method":"POST","path":"/api/v1/posts","status":200,"code":0,"cost_ms":86,"event":"post_created","extra":{"post_id":"13","image_count":3}}
```

| 字段 | 类型 | 说明 |
|---|---|---|
| `ts` | string | `YYYY-MM-DD HH:mm:ss.SSS`（Asia/Shanghai） |
| `level` | string | DEBUG/INFO/WARN/ERROR |
| `logger` | string | 模块名，如 `app.services.post_service` |
| `request_id` | string | 贯穿字段 |
| `user_id` | string\|null | 登录用户；游客为 null |
| `method` / `path` | string | 仅访问日志 |
| `status` / `code` | int | HTTP 状态 / 业务码 |
| `cost_ms` | int | 耗时 |
| `event` | string | 业务事件名（见第 5 节），访问日志为 `http_access` |
| `extra` | object | 业务字段，禁止放敏感信息 |
| `error` | object | 仅 ERROR：`type`、`message`、`stack`（截断 4KB） |

**实现**：`app/core/logging.py` 用标准 `logging` + 自定义 `JsonFormatter`；同时输出一份人读格式到 stdout（容器日志）。

## 3. 日志级别使用

| 级别 | 用在哪 | 例子 |
|---|---|---|
| DEBUG | 本地开发；生产关闭 | SQL 参数、缓存命中 |
| INFO | 关键业务动作 | 登录成功、发布成功、上传完成、限流触发 |
| WARN | 可恢复异常 | 微信接口超时重试、计数对账偏差、慢请求（>2s） |
| ERROR | 影响用户的失败 | 未捕获异常、DB 连接失败、上传落盘失败 |

**禁止**：`print`；在 INFO 里打印完整请求体（可能含长文本）；在 ERROR 里打印 SQL 全参数（可能含敏感信息）。

## 4. 必打的 5 类日志

### 4.1 访问日志（中间件，每请求 1 条）

```python
event="http_access", method, path, status, code, cost_ms, request_id, user_id
```

### 4.2 登录日志

```json
{"level":"INFO","event":"wx_login","extra":{"openid_tail":"…ab12cd","is_new":false,"errcode":0,"cost_ms":182}}
```

### 4.3 业务写操作

| 事件 | 字段 |
|---|---|
| `post_created` | `post_id, image_count, topic_count, text_len` |
| `post_deleted` | `post_id, by=author\|admin` |
| `comment_created` | `post_id, comment_id, is_reply` |
| `like_toggled` / `collect_toggled` | `target_type, target_id, on` |
| `upload_ok` | `kind, bytes, mime, path` |
| `profile_saved` | `fields[]` |
| `rate_limited` | `scope, key, limit, window` |

### 4.4 慢请求 / 慢 SQL

```json
{"level":"WARN","event":"slow_request","cost_ms":2431,"path":"/api/v1/feed"}
{"level":"WARN","event":"slow_sql","cost_ms":812,"sql":"SELECT ... FROM posts ..."}
```

阈值：请求 >2000ms、SQL >500ms。

### 4.5 异常

```json
{"level":"ERROR","event":"unhandled","error":{"type":"OperationalError","message":"MySQL server has gone away","stack":"Traceback ..."},"request_id":"..."}
```

## 5. 错误码 → 定位路径

| code | 首查 | 再看 |
|---|---|---|
| 40001 | 前端传参（抓包） | 路由 schema 定义 vs 实际 body |
| 40101 | token 是否存在/过期/`aud` 是否对 | `JWT_SECRET` 是否两端一致、系统时间是否准确 |
| 40301 | 资源归属（`user_id` vs 当前用户） | 用户是否被禁用、内容是否 `hidden` |
| 40401 | 记录是否 `deleted/status` | 路由参数是否为空串 |
| 40901 | 唯一键冲突（点赞/收藏/关注/去重） | 前端是否重复提交 |
| 42201 | 业务校验分支 | 具体字段值（日志 `extra`） |
| 42901 | 限流键与阈值 | 是否有刷接口行为 |
| 50000 | 日志 `event=unhandled` 的堆栈 | 最近一次发布/迁移 |
| 50300 | DB/存储连通性 | `/healthz` 的 `db` 字段 |

## 6. 排查手册

### 6.1 用户说"打不开/一直转圈"

1. 让用户复述时间与页面，取 `requestId`（前端错误上报里有）。
2. `grep '"request_id":"<rid>"' app.log` → 看 `http_access` 的 `status/cost_ms`。
3. 无该 rid → 请求未到后端：查 Nginx `access.log`、小程序合法域名、网络。
4. `cost_ms` 很大 → 看 `slow_sql`；`status=502` → 看容器存活。

### 6.2 401 循环

| 检查 | 命令/位置 |
|---|---|
| 两端 JWT_SECRET | `docker compose exec api env \| grep JWT` 对比部署记录 |
| token 的 `aud` | 解 token：`python -c "import jwt;print(jwt.decode(t,options={'verify_signature':False}))"` |
| 服务器时间 | `date`（偏差 >60s 会导致 exp 校验失败） |
| 前端是否无限重登 | 日志中同 `user_id` 的 `wx_login` 频率 |

### 6.3 500 定位

```bash
grep '"level":"ERROR"' app.log | tail -20
grep '"event":"unhandled"' app.log | jq -r '.error.stack' | head -40
```

对照 `request_id` 找同请求的 `http_access` 与业务日志，确认是"参数问题"还是"代码缺陷"。

### 6.4 上传失败

| 现象 | 查 |
|---|---|
| 413 | Nginx `client_max_body_size` |
| 42201 | 文件类型/大小（日志 `mime`、`bytes`） |
| 50300 | `UPLOAD_DIR` 是否挂载、磁盘是否满（`df -h`） |
| 成功但图片 404 | `UPLOAD_URL_PREFIX` 与 Nginx `/static/` 路径是否对应 |

### 6.5 数据不一致（计数偏差）

```bash
docker compose exec api python -m scripts.reconcile --dry-run
```

对比 `posts.like_count` 与 `COUNT(likes)`，偏差记录到日志 `event=reconcile_diff`；确认后 `--apply` 修正。

### 6.6 中文乱码 / 时间差 8 小时

| 现象 | 定位 |
|---|---|
| 乱码 | 连接串 `charset=utf8mb4`；库/表 `COLLATE`；Nginx 编码 |
| 差 8 小时 | 容器 `TZ`；MySQL `--default-time-zone=+08:00`；`datetime.now()` 是否用了 UTC |

### 6.7 限流误伤

日志 `event=rate_limited` 的 `scope/key`；若是 NAT 出口共用 IP，改为按 `user_id` 限流（已登录场景）。

## 7. 常用检索命令

```bash
# 单请求全链路
grep '"request_id":"8f3c1a2b9d4e"' /data/jianheng/logs/app.log | jq .

# 最近 50 条错误
grep '"level":"ERROR"' /data/jianheng/logs/app.log | tail -50 | jq -r '[.ts,.event,.error.message]|@tsv'

# 某接口慢请求
grep '"event":"slow_request"' app.log | jq -r 'select(.path=="/api/v1/feed")|[.ts,.cost_ms]|@tsv'

# 每分钟 5xx 数量（粗略）
grep '"status":5' app.log | awk -F'"ts":"' '{print substr($2,1,16)}' | sort | uniq -c

# 限流统计
grep '"event":"rate_limited"' app.log | jq -r '.extra.scope' | sort | uniq -c
```

> 生产若未装 `jq`，可先用 `grep` 定位行号，再用 `python -m json.tool` 美化。

## 8. 前端配合

| 项 | 要求 |
|---|---|
| 保存 | `request.js` 把最近一次 `X-Request-Id` 写入 `store.ui.lastRequestId` |
| 上报 | 接口失败时 `POST /track`，`event=api_error`，`props={api, code, requestId, page}` |
| 展示 | 错误弹层的"复制诊断信息"按钮复制 `requestId + 时间 + 页面` |
| 节流 | 同 `api` 60s 内最多 3 条，避免断网刷屏 |
| 禁止 | 上报 token、完整内容文本、用户 ID 明文（用哈希或省略） |

后端在 `track` 落库时补 `request_id`，形成"前端事件 ↔ 后端日志"的双向索引。

## 9. 脱敏规范

| 数据 | 处理 |
|---|---|
| token | 完全禁止打印 |
| `open_id` | 仅保留后 6 位：`…ab12cd` |
| `session_key` | 禁止出现 |
| 用户手机号 | 1.0 不采集；若未来采集，中间 4 位打码 |
| 帖子正文 | ERROR 日志不打印全文，截断 50 字 |
| `props`（埋点） | 禁止含以上三项 |
| IP | 存储时保留前两段（`10.72.*.*`） |

## 10. 轮转与保留

| 项 | 配置 |
|---|---|
| 应用日志 | `TimedRotatingFileHandler(when="midnight", backupCount=7)`，单文件 ≤50MB |
| 容器 stdout | `json-file`，`max-size=50m`，`max-file=3` |
| Nginx | `access.log` 按天轮转，保留 7 天 |
| 埋点表 | 保留 90 天，每日任务清理 |
| 备份 | 数据库 7 天，上传文件 4 周 |

## 11. 告警阈值（1.0 人工巡检）

| 指标 | 阈值 | 动作 |
|---|---|---|
| 5xx 比例 | >1%（5 分钟内） | 立即看 `unhandled` 堆栈 |
| P95 响应 | >1.5s | 查 `slow_sql` 与 DB 连接数 |
| `/healthz` 非 200 | 连续 3 次 | 重启 API，检查 DB |
| 磁盘 | >80% | 清日志/备份，扩盘 |
| 登录失败率 | >20% | 查微信 `errcode` 分布 |
| 上传失败率 | >5% | 查存储与 Nginx 限制 |

## 12. 日志规范检查清单

- [ ] 每个请求都有 `request_id`，响应头与响应体一致
- [ ] 访问日志含 `method/path/status/code/cost_ms/user_id`
- [ ] 登录、发布、上传、限流、删除均有业务事件
- [ ] ERROR 日志含 `type/message/stack` 且截断 4KB
- [ ] 慢请求（>2s）与慢 SQL（>500ms）有 WARN
- [ ] 无 token / `session_key` / 完整正文 泄漏
- [ ] `open_id` 已脱敏
- [ ] 日志按天轮转且保留 7 天
- [ ] `grep request_id` 能串起"请求 → 业务 → 异常"三段
